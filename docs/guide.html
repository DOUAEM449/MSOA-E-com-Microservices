E-commerce en microservices

DDouae · Orders + Intégration · Leader AAmal · Inventory YYoussef · Auth SSalma · Catalog TTaha · Payments + Shipping

C'est quoi un microservice ?

Un microservice est une petite application indépendante qui s'occupe d'une seule capacité métier, qui a sa propre base de données, et qui parle aux autres uniquement via une API REST (HTTP + JSON).

Avant : le monolithe

Un seul backend fait tout : produits, stock, commandes, paiements. Une seule base de données. Un petit changement dans le stock oblige à redéployer toute l'application, et un bug peut tout faire tomber.

Après : 6 microservices

6 programmes séparés, chacun sur son port, avec sa base. On peut modifier, redéployer ou faire monter en charge un seul service (par exemple Catalog pendant les promos) sans toucher aux autres.

Les 4 principes qu'on doit respecter (et que le prof va vérifier)

1. Forte cohésion

Tout ce qui est dans un service concerne le même métier. Inventory ne gère que le stock, pas les prix.

2. Faible couplage

Un service connaît seulement le contrat REST des autres, jamais leur code ni leur base.

3. Autonomie

Chaque service démarre, se teste et se déploie seul : python main.py ou npm start, et il marche.

4. Propriété des données

Chaque service est le seul à lire et écrire sa base. Pour avoir une info d'un autre service, on appelle son API.
Le rôle du frontendLe React fourni est déjà fini. Il fonctionne en mode mock (données simulées dans le navigateur). Notre travail : construire les vrais backends, puis passer chaque service de "mock" à "rest" dans src/config/backend.js.

Flux d'une commande (Q4 du TP)

Voici exactement ce que fait la page Checkout du frontend (src/pages/Checkout.jsx), et ce que chaque backend doit faire en coulisse.

  1. Vérifier le stockFrontend → Inventory
    POST /api/inventory/check → {"available": true}. Simple vérification, rien n'est modifié.
  2. Créer la commandeFrontend → Orders → Catalog + Inventory
    Orders récupère les vrais prix chez Catalog, calcule le total, puis appelle POST /api/inventory/reserve. Si la réservation échoue → erreur 409 et la commande n'est pas créée. Sinon → statut PENDING_PAYMENT.
  3. PayerFrontend → Payments → Orders
    Payments lit la commande (GET /api/orders/{id}) pour connaître le montant, simule le paiement (SUCCESS), puis met la commande en PAID (PATCH /api/orders/{id}/status).
  4. ExpédierFrontend → Shipping → Orders
    Shipping vérifie que la commande est PAID, crée l'expédition avec un numéro de suivi, statut PREPARING.
  5. SuiviFrontend → Shipping puis Orders
    Le composant ShipmentTracker avance l'expédition, puis met lui-même la commande à SHIPPED / DELIVERED.
Et si le stock est insuffisant ?Inventory refuse toute la réservation (atomique : soit tous les produits, soit aucun). Orders renvoie une erreur 409 avec {"message": "..."} et ne crée pas la commande. Si un problème arrive après la réservation (ex. erreur en base), Orders appelle /release pour rendre le stock : c'est la compensation (pattern Saga, orchestré par Orders).

Cycle de vie d'une commande

StatutQui le metAnnulation possible ?
PENDING_PAYMENTOrders (création)Oui → libère le stock
PAIDPayments (via PATCH)Oui → libère le stock
SHIPPEDFrontend (via PATCH)Non → 409
DELIVEREDFrontend (via PATCH)Non → 409
CANCELLEDOrders (cancel)déjà annulée → 409

Règles d'or

🚫 On ne touche pas au React

Interdit de modifier src/pages, src/components, src/services. Le seul fichier qu'on change : src/config/backend.js.

📜 Le contrat REST est sacré

Mêmes méthodes HTTP, mêmes chemins, mêmes noms de champs JSON (en camelCase : productId, createdAt…). Une seule lettre différente et le frontend casse.

🗄️ Une base par service

Personne ne lit la base d'un autre. Pas de jointure entre orders.db et catalog.db. Les IDs (productId, userId…) sont de simples références.

🔌 Communication = REST seulement

Pour une info d'un autre service, on appelle son API. Les URLs des autres services se mettent dans une variable de config, jamais en dur partout dans le code.

🌐 CORS obligatoire

Chaque service autorise l'origine http://localhost:5173 (méthodes GET, POST, PATCH, OPTIONS ; en-têtes Content-Type, Authorization).

❗ Format d'erreur commun

Toujours {"message": "texte lisible"} avec le bon code : 400 données invalides, 401 non connecté, 404 introuvable, 409 conflit métier, 503 service dépendant indisponible.

💰 Ne jamais faire confiance au frontend

Les prix, le stock et les droits viennent toujours du backend. Le frontend envoie seulement productId + quantity.

🧩 Liberté de technologie

Chacun choisit sa stack (Spring Boot, FastAPI, Express…). Seul le contrat compte. Chaque service a un README.md avec la commande pour le lancer.

Douae — Orders + Intégration

Port 8084 · services/orders · base orders.db
Orchestrateur + Leader

Orders est le cœur du système : c'est lui qui coordonne la création d'une commande (Saga orchestrée). Il ne gère pas le stock lui-même, il demande à Inventory.

Endpoints

MéthodeCheminCe qu'il fait
GET/api/orders?userId={id}Liste des commandes de cet utilisateur uniquement
GET/api/orders/{id}Une commande (404 si inconnue). Utilisé aussi par Payments et Shipping
POST/api/ordersCrée la commande (voir algorithme)
PATCH/api/orders/{id}/statusBody {"status":"PAID"}, seulement les transitions autorisées
POST/api/orders/{id}/cancelAnnule si PENDING_PAYMENT ou PAID, libère le stock ; sinon 409

Algorithme de POST /api/orders

  1. Valider le body : userId, customer{name,address,city}, items non vide, quantity > 0 → sinon 400.
  2. Pour chaque produit : GET {CATALOG}/products/{productId} → récupérer name et price (404 → 400 « produit inconnu »).
  3. Calculer total = Σ price × quantity.
  4. POST {INVENTORY}/api/inventory/reserve avec {"items":[{productId,quantity}]}. Si échec → 409 et on s'arrête.
  5. Insérer orders + order_items dans une transaction, statut PENDING_PAYMENT, id du type order-xxxx.
  6. Si l'insertion échoue → appeler /api/inventory/release (compensation) puis 500.
  7. Répondre 201 avec la commande au format attendu.

Format de réponse

{
  "id": "order-1a2b3c", "userId": "user-1",
  "customer": { "name": "Demo Customer", "address": "123 Main Street", "city": "Casablanca" },
  "items": [ { "productId": 1, "name": "Lenovo ThinkPad E14", "price": 8499, "quantity": 2 } ],
  "total": 16998, "status": "PENDING_PAYMENT", "createdAt": "2026-11-06T10:00:00Z"
}
Pièges spécifiquesLa base stocke customer_name, customer_address… à plat : il faut les regrouper dans un objet customer en sortie. order_items.product_id → productId. Mettre un timeout (3 à 5 s) sur les appels vers Catalog/Inventory, et renvoyer 503 s'ils ne répondent pas.

Tâches de leader

  • Organiser la réunion Partie I et consolider docs/answers.md + Q6.
  • Relire et merger les Pull Requests.
  • Fixer un point d'avancement court (2 fois par semaine).
  • Piloter le test d'intégration final avec les 6 services en "rest".

Terminé quand…

  • Une commande réserve le stock et apparaît dans « Orders » côté frontend
  • Stock insuffisant → message d'erreur clair, rien n'est créé
  • Annulation → stock restauré ; commande expédiée → annulation refusée
  • Un utilisateur ne voit que ses propres commandes

Amal — Inventory

Port 8083 · services/inventory · base inventory.db
Service critique

Inventory est la seule source de vérité du stock. Sa règle la plus importante : la réservation est atomique.

Endpoints

MéthodeCheminRéponse
GET/api/inventory/{productId}{"productId":1,"stock":12} (le frontend lit data.stock)
POST/api/inventory/check{"available":true|false}, ne modifie rien
POST/api/inventory/reserve{"success":true} ou 409 {"message":"Insufficient stock for product 3"}
POST/api/inventory/release{"success":true}, rajoute les quantités

Body des 3 POST : {"items":[{"productId":1,"quantity":2}]}

Réservation atomique : la bonne façon

BEGIN IMMEDIATE;                       -- verrouille l'écriture (SQLite)
-- pour chaque item : vérifier quantity >= demandé, sinon ROLLBACK + 409
UPDATE stock SET quantity = quantity - ?, updated_at = ?
 WHERE product_id = ? AND quantity >= ?;   -- 0 ligne modifiée → ROLLBACK
COMMIT;
Pièges spécifiquesRéserver produit par produit sans transaction : si le 3e manque, les 2 premiers sont déjà décomptés (c'est exactement ce que le prof teste). Oublier le cas d'un même productId présent deux fois dans items. Accepter des quantités négatives ou nulles (→ 400). Produit inconnu → 404 sur GET, et indisponible sur check.
Synchroniser les donnéesMettre les quantités de inventory.db égales aux stock de src/data/products.js (12, 20, …) pour que le mode REST ressemble au mode mock.

Terminé quand…

  • Les cartes produits affichent « N available » venant de la base
  • Une réservation dépassant le stock ne change aucune quantité
  • Release restaure exactement ce qui a été réservé

Youssef — Auth

Port 8081 · services/auth · base auth.db
Sécurité

Auth gère l'inscription, la connexion et l'identité de l'utilisateur connecté. Le frontend envoie ensuite le token dans l'en-tête Authorization: Bearer <token> à tous les services.

Endpoints

MéthodeCheminBody → Réponse
POST/api/auth/register{name,email,password} → 201 {user} ; email déjà pris → 409
POST/api/auth/login{email,password} → {"user":{id,name,email,role},"token":"..."} ; mauvais identifiants → 401
POST/api/auth/logoutinvalide le token → 200 ou 204
GET/api/auth/melit le Bearer token → {id,name,email,role} ; invalide → 401
Piège n°1 : le mot de passe du seedDans auth.db, password_hash vaut DEMO_ONLY_REPLACE_WITH_REAL_PASSWORD_HASH : ce n'est pas un vrai hash, la connexion échouera. Il faut remplacer cette valeur par le hash bcrypt de demo123 (garder id = user-1 pour que les commandes de démo restent liées).
Autres piègesStocker le mot de passe en clair (interdit : utiliser bcrypt / argon2). Renvoyer password_hash dans la réponse JSON. Email sensible à la casse : faire trim().toLowerCase(). Clé secrète du JWT écrite en dur et commitée → la mettre dans une variable d'environnement.

Token : un JWT (signé, avec sub = id utilisateur et une expiration) est le plus simple. Pour logout avec un JWT, garder une petite liste de tokens révoqués.

Terminé quand…

  • Connexion avec demo@msoa.shop / demo123 en mode REST
  • Inscription d'un nouveau compte puis connexion
  • Rafraîchir la page garde la session (via /me)

Salma — Catalog

Port 8082 · services/catalog · base catalog.db
Premier à brancher

Catalog est le service le plus simple (lecture seule). C'est le premier qu'on passe en "rest" : il sert de modèle aux autres (CORS, structure, README).

Endpoints

MéthodeCheminRéponse
GET/productstableau de produits
GET/products/{id}un produit, ou 404

Produit : {"id":1,"name":"...","category":"...","price":8499,"image":"https://...","description":"..."}

Piège n°1 : pas de préfixe /apiContrairement aux 5 autres services, le frontend appelle /products et non /api/products. Respecter exactement.
Piège n°2 : les données du seed ne correspondent pasLe seed contient « ThinkPad Laptop, Wireless Mouse… » alors que le frontend mock a « Lenovo ThinkPad E14, Samsung Galaxy A55… » avec d'autres prix et catégories. Il faut mettre à jour catalog.db avec les 6 produits de src/data/products.js (mêmes id, noms, prix, images).
Ce que Catalog ne fait pasIl ne renvoie pas le stock : le frontend le demande à Inventory pour chaque produit. Garder cette séparation (cohésion).

Terminé quand…

  • /products/999 renvoie 404 avec {"message"}

Taha — Payments + Shipping

Ports 8085 et 8086 · services/payments, services/shipping
2 services séparés
Deux services, pas un seulMême si une seule personne les code, ce sont deux applications séparées : deux projets, deux ports, deux bases. Ne pas les fusionner dans un seul serveur.

Payments — 8085

MéthodeCheminCe qu'il fait
GET/api/paymentsliste des paiements
GET/api/payments/order/{orderId}paiement d'une commande, ou 404
POST/api/paymentsbody {"orderId","method"} → paiement SUCCESS
  1. GET {ORDERS}/api/orders/{orderId} → 404 si inconnue ; doit être PENDING_PAYMENT sinon 409.
  2. Le montant = order.total (jamais envoyé par le frontend).
  3. Déjà un paiement pour cette commande → 409 (order_id est UNIQUE).
  4. Enregistrer {id, orderId, amount, method, status:"SUCCESS", createdAt}.
  5. PATCH {ORDERS}/api/orders/{orderId}/status avec {"status":"PAID"}.

Shipping — 8086

MéthodeCheminCe qu'il fait
GET/api/shipmentsliste des expéditions
GET/api/shipments/order/{orderId}expédition d'une commande, ou 404
POST/api/shipmentsbody {"orderId","address":{name,address,city}}
PATCH/api/shipments/{id}/statusbody {"status":"SHIPPED"}, une étape à la fois

À la création : vérifier que la commande est PAID (sinon 409), générer un trackingNumber unique (ex. MSOA-7F3K2A), statut PREPARING. Réponse : {id, orderId, address:{name,address,city}, trackingNumber, status, createdAt, updatedAt}.

Transitions autorisées uniquement : PREPARING → SHIPPED → IN_TRANSIT → DELIVERED. Sauter une étape ou revenir en arrière → 409.

Pièges spécifiquesDans la base, l'adresse est à plat (recipient_name, address, city) : il faut la regrouper dans un objet address avec la clé name. Ne pas oublier de mettre à jour updated_at à chaque changement. Si Orders ne répond pas → 503, ne pas créer le paiement quand même.

Terminé quand…

  • Après un checkout, la commande passe à PAID et a une expédition
  • Le tracker avance étape par étape jusqu'à DELIVERED
  • Payer deux fois la même commande est refusé

Pièges à éviter (toute l'équipe)

CORS oubliéErreur « blocked by CORS policy » dans la console du navigateur. Penser aussi à répondre aux requêtes OPTIONS (preflight), surtout pour PATCH et l'en-tête Authorization.
Mauvais nom de champproduct_id au lieu de productId, created_at au lieu de createdAt. La base est en snake_case, l'API en camelCase : convertir.
Monolithe distribuéUn service qui ouvre la base d'un autre, ou un « service commun » qui fait tout. C'est la mauvaise décomposition que le prof demande d'identifier en Q3.
Re-seed d'une base déjà remplieLes .db fournis contiennent déjà les données. Relancer seed.sql dessus → erreurs de clé dupliquée. Faire une copie avant de modifier.
Prix venant du frontendCalculer le total avec un prix reçu du navigateur = n'importe qui peut payer 1 DH. Toujours relire le prix chez Catalog.
Mauvais portLe frontend appelle exactement 8081 à 8086. Vérifier qu'aucun autre programme n'utilise déjà le port.
Réponse vide ou HTMLLe frontend fait JSON.parse : une page d'erreur HTML (par défaut dans Spring ou Express) casse tout. Toujours renvoyer du JSON.
Tout tester à la finBrancher les 6 services le dernier jour = impossible de savoir qui casse quoi. Brancher un par un, dès qu'un service est prêt.

Astuces

Stub en 10 lignes

Douae n'a pas encore Inventory ? Un petit serveur sur 8083 qui répond toujours {"success":true} suffit pour avancer. Même chose pour Taha avec un faux Orders.

URLs en variables d'environnement

CATALOG_URL=http://localhost:8082, INVENTORY_URL=…. On passe du stub au vrai service sans toucher au code.

Onglet Network du navigateur

F12 → Network : on voit la requête exacte envoyée par le frontend (URL, body) et la réponse. C'est le meilleur outil pour vérifier le contrat.

Collection Postman partagée

Une requête par endpoint, exportée dans docs/postman/. Les captures servent directement de « preuves de tests ».

Script de démarrage

Un start-all.bat (ou .sh) à la racine qui lance les 6 services : la démo finale se fait en une commande.

Logs lisibles

Préfixer chaque log par le service : [orders] reserve failed: 409. Très utile pour suivre une commande qui traverse 4 services.

Script de reset

Garder une copie propre de chaque .db (ou un script qui la recrée) pour revenir à l'état initial avant la démo.

Copier la structure de Catalog

Le premier service terminé (CORS, format d'erreur, README) sert de modèle. Ceux qui utilisent la même stack copient le squelette.
