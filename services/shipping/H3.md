# LAB 4 H3 — Vérifier le consumer Shipping

Depuis la racine du dépôt, dans PowerShell, pour démarrer Shipping sur la configuration
d’équipe. Orders doit être disponible sur le port 8084 pour créer de nouvelles
expéditions. Le démarrage de Shipping et une répétition validée d’un POST restent
possibles pendant une panne d’Orders ou de RabbitMQ.

```powershell
docker compose up -d rabbitmq
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r services/shipping/requirements.txt
.\.venv\Scripts\python.exe services/shipping/main.py
```

La file est visible dans RabbitMQ Management à l’adresse
`http://localhost:15672/#/queues/%2F/shipping_requests` (identifiants locaux
`guest` / `guest`). Pour un essai avec les services d’équipe, effectuer un paiement
sur une commande préparée via Orders, puis chercher l’expédition par
`GET http://localhost:8086/api/shipments/order/<orderId>`.

## Suite automatisée H3

La suite utilise AMQP, RabbitMQ Management et SQLite réels. Elle lance le consumer
Shipping dans des processus enfants, utilise une base temporaire et simule un
Orders qui répond `PAID`. Elle neutralise Kafka. Le processus de crash intercepte
`basic_ack` dans le code de test, après le commit SQLite. Le processus parent le
termine seulement après avoir observé une ligne SQLite et un message Unacked.

Utiliser un broker de test dédié. Depuis la racine du dépôt, exécuter ces commandes.

```powershell
docker run -d --rm --name msoa-shipping-h3 -p 127.0.0.1:25672:5672 -p 127.0.0.1:25673:15672 rabbitmq:3.13-management
docker exec msoa-shipping-h3 rabbitmq-diagnostics -q ping
$env:H3_RABBITMQ_URL = 'amqp://guest:guest@127.0.0.1:25672/%2F'
$env:H3_MANAGEMENT_URL = 'http://127.0.0.1:25673'
Push-Location services/shipping
..\..\.venv\Scripts\python.exe -m unittest discover -s tests -v
..\..\.venv\Scripts\python.exe -m tests.h3_rabbitmq
Pop-Location
docker stop msoa-shipping-h3
```

Attendre que le diagnostic renvoie `Ping succeeded` avant de lancer la suite.
Pour prendre les captures automatiquement, installer Playwright dans la venv et
indiquer le dossier de sortie avant de relancer `tests.h3_rabbitmq`. Le navigateur
utilisé est Microsoft Edge.

```powershell
.\.venv\Scripts\python.exe -m pip install playwright
$env:H3_CAPTURE_DIR = Join-Path (Get-Location) 'services/shipping/evidence'
```

| Scénario | RabbitMQ Management | Logs et vérification SQLite |
| --- | --- | --- |
| 1. Normal, `test_1_normal` | Ready 0, Unacked 0, ACK +1 après publication | `created=True`, `ACK … redelivered=False`, une ligne pour l’ordre |
| 2. Arrêt, `test_2_shipping_offline` | Consumer arrêté, Ready 1 et Unacked 0. Après redémarrage, Ready 0, Unacked 0 et ACK +1 | Aucune ligne pendant l’arrêt. Après reprise, `created=True` et une ligne |
| 3. Crash, `test_3_crash_before_ack` | Avant crash, Ready 0, Unacked 1. Après crash, Ready 1, Unacked 0. Après redémarrage, Ready 0, Unacked 0 et ACK +1 | Une ligne déjà visible avant le crash. À la reprise, `created=False` et `ACK … redelivered=True`. La ligne garde le même identifiant |

La suite couvre aussi une panne temporaire d’Orders. Après une réponse `503`,
elle vérifie que RabbitMQ redélivre le message sans redémarrage manuel de Shipping.

## Preuves de l’exécution H3

Les trois scénarios ont réussi avec RabbitMQ 3.13.7. Les captures montrent la file
du broker isolé. Le compte d’ACK et les lignes SQLite ont été vérifiés par le test.

- Scénario 1. Le compteur ACK est passé de 1 à 2 et SQLite contenait une expédition. [File après ACK](evidence/h3-1-normal.png)
- Scénario 2. Pendant l’arrêt, Ready valait 1 et SQLite contenait zéro ligne pour la commande. Après redémarrage, le compteur ACK est passé de 2 à 3 et SQLite contenait une ligne. [File pendant l’arrêt](evidence/h3-2-offline.png) · [File après reprise](evidence/h3-2-restarted.png)
- Scénario 3. Le compteur ACK est resté à 3 pendant la transition Unacked vers Ready. Après redélivrance, le compteur est passé à 4 et SQLite contenait toujours une seule ligne. Les deux passages du consumer ont journalisé le même identifiant `shipment-68d77a6e`, avec `created=True` puis `created=False`. [Avant crash](evidence/h3-3-unacked.png) · [Après crash](evidence/h3-3-ready.png) · [Après redélivrance et ACK](evidence/h3-3-redelivered.png)
